# Эксплуатация

## Проверить состояние

Начинайте с идентификатора попытки и выбранного Kubernetes-контекста. У попытки K8S namespace называется `lab-<UUID>`, а в панели CMS есть отдельный числовой ID записи.

```bash
kubectl config current-context
kubectl -n cms-labs-system get deploy,pods,cronjob
kubectl get topology -A
kubectl -n "$LAB_NAMESPACE" get pods,pvc,svc
kubectl -n "$LAB_NAMESPACE" get events --sort-by=.lastTimestamp
```

Укажите в `LAB_NAMESPACE` значение из вкладки **«Обзор»**. Если платформа установлена в другом системном namespace, подставьте его в первую команду просмотра. При ошибке обратитесь к [диагностике по симптомам](troubleshooting.md).

| Сигнал | Где смотреть |
| --- | --- |
| Попытки, статус и сохранённые проверки | Главная CMS и список «Попытки LTI». |
| Топологии, готовность узлов и контроллеры | Clabernetes CRD и dashboard Grafana, если он настроен. |
| Долгий запуск | Сравните время создания попытки с этапами в обзоре; в Kubernetes проверьте readiness, PVC и события. |
| Ошибка checker | Результат в панели, checker Job и его pod. Дополнительные детали могут быть в логах Clabgate. |
| Оценка не ушла в Moodle | Отметка «Отправлено в» и результаты `grade-sync`. |
| CPU, RAM, storage | Панели ресурсов по namespace. Для CPU/RAM можно использовать `kubectl top pods`, если доступен Metrics API. |

## Обновить и откатить

1. Зафиксируйте версии чарта, образов, текущий `helm history` и конфигурацию. Сделайте резервную копию MySQL перед изменением версии backend.
2. Прогоните обновление на тестовой среде. Проверьте запуск новой работы, доступ к терминалу и JupyterLab, результат checker и тестовую отправку оценки.
3. Обновите рабочий Helm release с явной версией и дождитесь readiness. Выполните короткую проверку под тестовой учётной записью.
4. При сбое приложения выполните `helm rollback <release> <revision> --namespace <namespace> --wait` после проверки, что текущая схема базы совместима с прошлым образом. Helm откатывает Kubernetes-ресурсы; миграции MySQL и содержимое PVC откатываются отдельной процедурой.

| Что сохранить | Что проверить при восстановлении |
| --- | --- |
| MySQL | Дамп или резервная копия провайдера восстанавливается в отдельную базу. Сверьте пользователей, интеграции, маршруты и оценки. |
| Ключи и конфигурация | Сохраните JWT-ключи, ключ workspace и настройки интеграций в хранилище секретов. Замените их после инцидента, если этого требует процедура. |
| Notebook и артефакты | До завершения попытки экспортируйте файлы или сделайте согласованный снимок PVC со стороны хранилища. |
| Манифесты платформы | Сохраните Git revision, значения конфигурации без секретов и версии используемых образов. |

Периодически восстанавливайте копию в тестовое окружение и измеряйте длительность восстановления. Периодичность резервирования и допустимая потеря данных определяются требованиями курса.
